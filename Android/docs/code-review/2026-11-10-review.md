## 逐条核对

### 7. 入库弹窗持锁等待用户

**原问题**：`choose()` 把 `deferred.await()` 包在 `gate.withLock` 里，第二个调用方静默排队，不弹窗、无进度、无错误。

**现状**：锁只包「登记」这一段（`data/BiliImportRequests.kt:49-58`）：持有锁时若已有 `answer`，调用 `busy()` 并返回 null；否则分配 id、写入 `answer` 与 `prompt`。`deferred.await()` 在锁外（`:60`），清理放在 `NonCancellable` + 重新加锁中，并用 `answer === deferred` 判等后才清（`:62-71`），不会清掉后来者。

**核对结论**：正确。第二个调用方立即返回而非等待；取消路径仍清理弹窗；四个调用方对 null 的处理不需要改动。`busy()` 在锁内执行，但只是写全局 snackbar，非挂起、不会引入新锁。

**验证**：`BiliImportRequestsTest` 新增 3 个用例——`busyPromptRejectsSecondRequestWithoutQueueing`、`promptIsReusableAfterTheFirstRequestFinishes`、`cancellingTheCallerStillClearsThePrompt`，全部通过。

### 6. B 站续期失败仍标记「已检查」

**原问题**：`refreshSession` 在 csrf 缺失、解析失败、服务端拒绝、newCsrf 缺失时静默 return；`maybeRefreshSession` 随后无条件 `markBiliRefreshChecked()`，导致约 20 小时不再尝试且界面无提示。

**现状**：`refreshSession` 改为返回 `Boolean`（`bilibili/BilibiliClient.kt:559-607`）：所有失败分支 `return false`；`saveBiliSession` 之后即视为成功（`:593` 的 newCsrf 缺失返回 true，confirm 非 0 仅记日志）。`maybeRefreshSession` 仅在成功（或不需要续期）时 `markBiliRefreshChecked`，否则 `markBiliRefreshFailed`（`:544-556`），`cookie/info` 读取异常同样记失败。失败标记落普通偏好 `bili_refresh_failed_at`（`data/CredentialStore.kt:399`），调度纯函数 `biliRefreshDueAt`（`:13-18`）先判 10 分钟失败冷却，再判 20 小时成功间隔；`markBiliRefreshChecked`、`saveBiliSession`、`clearCookie`、内容变化的 `saveCookie` 都清除失败标记。UI 在 `biliCanRefresh && biliRefreshFailed` 时显示「自动续期失败，请重新登录」（`ui/asmr/OnlineScreens.kt:2237`），失败状态通过 `MutableStateFlow` 驱动（`data/CredentialStore.kt:28-30`）。

**核对结论**：正确。会话失效时最多冷却 10 分钟而不是 20 小时；离线时不会每次请求都打网络；日志仍只输出响应码与异常类名。

**验证**：`BiliRefreshScheduleTest` 3 个用例（首次立即检查、成功后 20 小时内不查、失败 10 分钟后重试），全部通过。

### 5. Qwen 轮询无总超时

**原问题**：`poll` 是 `while(true)` + `delay(2000)`，无总超时；`WhisperCenter.drain` 串行，一个卡死任务阻塞后面全部听写。

**现状**：`withTimeout(QWEN_POLL_TIMEOUT_MS)` 只包住 `poll`（`data/QwenFileTranscriber.kt:38`），常量 30 分钟（`data/WhisperModels.kt:14`）。只捕获 `TimeoutCancellationException` 并转为 `WhisperException("听写超时，请重试")`（`:39-42`）；用户中止仍是 `CancellationException`，不会被误判为超时。上传、提交、下载各有独立超时，不受影响。

**核对结论**：正确，且不会把「用户中止」显示成失败。**一点说明**：轮询请求是阻塞的 `call.execute()`（`:184`），`withTimeout` 不能在阻塞期间打断它，超时要到下一次 `delay(2000)` 才被观察到，因此实际失败时刻 ≈ 30 分钟 + 当前在途请求（读超时 2 分钟，`:27`）。`:41` 的 `calls.cancel` 在 catch 里执行，此时当前请求已经返回，属于防御性清理；它不能缩短上面这最多 2 分钟的溢出。这仍然满足「不永久占住串行队列」的目标，无需再改。

**验证**：编译通过；超时行为依赖设备验收（把 base 指向恒返回 PENDING 的桩）。

### 1. 远端单文件下载同名覆盖

**原问题**：`downloadRemote` 用 `workKey/fileName(job)` 作目标，`fileName` 只取标题，丢掉子目录；同一作品不同子目录的同名文件互相覆盖，`localCopy` 只检查文件存在，会把 A 的播放 / 听写指向 B 的音频。

**现状**：目标路径改由 `remoteDestination` 计算（`data/DownloadCenter.kt:705-727`，调用点 `:569`）：
1. 同 `rawFileKey` 且已落盘的下载记录（`locatedForWork`，`data/db/Daos.kt:249-251`，`localPath IS NOT NULL`，不限状态）→ 原样复用路径，保证同一文件重试与旁挂字幕稳定；
2. 否则用扁平 `workKey/fileName`；若文件已存在，或被同作品其他 `fileKey` 的记录占用（按 `canonicalPath` 比较），改落 `{8 位短哈希}/文件名`（`data/EntryNames.kt:63-71`）；
3. `fileKey` 为空（DLsite 试听）沿用扁平名。

`fileName`（`:643-654`）经 `sanitizeEntryName` 处理，不会带路径分隔符。已入库曲目仍走 `destination(track)` + `relativeDirs`，不受影响。下载由 `kick` 单协程串行执行，占用检测无并发竞态；`enqueueRemote` 的去重与插入在同一事务（`:276-298`）。

**核对结论**：正确。已落盘文件被复用而不是新建副本；同名不同 key 不再互相覆盖；`fileKey` 为空的试听保持旧行为（会覆盖，属预期）。4 字节哈希在同作品文件量级不构成现实碰撞风险。

**验证**：`RemoteDownloadPathTest` 4 个用例（同标题不同 key 分目录、同 key 路径恒定、未占用保持扁平、空 key 回退），全部通过。

### 2. 失败的原始包暂存永不清理

**原问题**：启动时 `failActive` 把中断任务标 FAILED 后，`filesDir/dlsite-archives/{workno}/{jobId}` 永久残留，且没有界面能删除它。

**现状**：
- 启动清理改为扫目录（`data/DownloadCenter.kt:231-244`）：`live` 集合 = 全部 DLSITE_ARCHIVE 任务中 `status != DONE` 的 `"$workKey/$id"`；只有 `(?:RJ|BJ|VJ)[0-9]+` 作品目录与纯数字任务子目录参与，不在 live 的一律删除，空作品目录一并删除。DONE 的残留也会清，FAILED / QUEUED / RUNNING 保留供断点续传。启动顺序是先 `failActive` 再清理（`:249-262`）。
- 新增 `deleteFailed(id)`（`:436-442`）：先 `get`，再走 DAO `DELETE ... AND status='FAILED'`（`data/db/Daos.kt:255-256`），返回 0 就不动磁盘；确认删除后才删该任务的暂存。若用户先点重试（任务转为 QUEUED / RUNNING），DELETE 返回 0，不会误删正在续传的目录。
- UI：失败行在「重试」旁增加「删除」，带二次确认；完整包任务的文案说明会删除已下载压缩包（`ui/download/DownloadScreen.kt:243-266`）。

**核对结论**：正确。删除入口与孤儿扫描互补：手动删除回收指定任务，启动清理兜住数据库里已无记录的目录；已发布副本与 `localPath` 不受影响。

**验证**：编译通过；暂存保留 / 删除 / 孤儿清理需设备验收。

### 3. 原始包发布冲突导致必然失败的重试

**原问题**：`DlsiteOriginalStore` 中 `check(owner == null || owner.id == track.id)` 一旦触发就整体回滚，`DownloadCenter` 统一报「原始压缩包处理失败，请重试」，重试必然再失败且看不到冲突文件。

**现状**：冲突分支改为跳过并保留原关联（`data/DlsiteOriginalStore.kt:174-182`）：记录 `skipped += item.path`，`usedTrackIds += owner.id`（阻止后续条目把 owner 的 `localUri` 改指到别的文件），清单条目仍指向真实占用者 `owner.id`，并保留 `playFileKey`，`linked` 不自增。结果类型新增 `skipped`（`:38`），`DownloadCenter` 在两个发布点接住返回值（`:99`、`:153-166`），在 `NonCancellable` 块外提示「已发布原始文件；N 个文件已关联其他曲目，保持不变」（`:182-186`），任务照常 DONE。

**核对结论**：正确。发布仍在一个事务里原子提交（`deleteEntries`/`upsertEntries` 不变）；单个冲突不再导致整包失败，重试不再必然失败。`audioCount` 现在可能包含被跳过文件的占用者，三个调用点原本就丢弃该返回值，无行为影响。

**验证**：`DlsiteOriginalStoreAndroidTest#conflictingFileIsSkippedAndKeepsItsExistingOwner` 已编译通过（未在设备上运行）。

### 4. 作品导入无事务 + 并发撞唯一索引

**原问题**：`importPlayNodes` / `importAsmrNodes` 逐条插入且不在事务内；`ensureWorkFiles` 的前置检查在事务外，两个入口可同时通过，撞 tracks 的 `(asmrWorkId, fileHash)` 唯一索引且无兜底，留下半个作品。

**现状**：
- 新增 `workImportLock`（`data/LibraryRepository.kt:85`），`ensureWorkFiles` / `ensureWorkSource` / `importAsmr` / `importPlayWork` 整个方法体（含网络）在锁内（`:156`、`:229`、`:596-609`、`:621-650`），前置查重在拿锁后重新判定；
- 插入阶段包 `db.withTransaction`：两个 fill 方法内的 4 处 `import*Nodes`（`:187,197,261,266`）、`importPlayWork` 的根目录插入 + `importPlayNodes`（`:627-641`）、`insertAsmrWork` 整个方法（`:684-699`；`ensureAsmrWork:678` 的既有事务会加入）；`restoreOriginalCopy`（内部有网络）留在事务外；
- 兜底：`importAsmr` / `importPlayWork` 捕获 `hasConstraint()` 后转成「这部作品已经在音频库」（`:603-608`、`:643-648`，判定在 `:1056`）。

**核对结论**：正确。锁不可重入，但已核对：锁内调用的都是私有 `fill*` / `import*Nodes` / `folderBySource` / `restoreOriginalCopy`，没有再次进入这四个加锁方法；`restoreOriginalCopy` → `DlsiteOriginalStore.importDirectory` 只调用不加锁的 `folderBySource`，而 `importDirectory` 也不获取 `archiveLock`，与 `enqueueDlsiteArchive`（持 `archiveLock`，不调用作品导入锁）之间没有锁序环。事务回滚后不会留下「有文件夹无曲目」的半截作品。

**验证**：编译通过；并发填充与断网中断需设备验收。

## 本轮审查与修复

审查范围为相对 `bc6b1fc` 的 Android 工作区改动，重点核对作品路径、下载管理、播放列表封面和界面文案。以下记录保留审查时的优先级。

### P2 · 取消本地关联的弹窗误报删除文件

对已关联的本地音频生成字幕后，点「取消本地关联」会显示删除音频和字幕的选项。实际操作只解除关联。混选下载副本和关联文件时，原弹窗也无法区分两类操作。

音频库和作品页现在按实际选中的曲目确定操作。仅有关联文件时直接解除关联，保留原文件和字幕。混选时分别确认下载副本数和解除关联的曲目数，字幕选项只取决于待删除的下载副本。执行前复核本地路径，跳过并报告路径已变化或曲目已移除的条目。实现见 [LibraryViewModel.kt](../../app/src/main/java/com/nanahoshi/audioplayer/ui/library/LibraryViewModel.kt) 和 [LocalRemoval.kt](../../app/src/main/java/com/nanahoshi/audioplayer/data/LocalRemoval.kt)。

### P2 · 原始包换版后可能停留在已隐藏的目录

DLsite 新版原始包移除当前子目录时，旧文件夹记录可能仍在数据库中。原路径校验只检查文件夹记录及父子关系，父目录已按新清单隐藏该入口，当前页面却仍会显示旧条目。

音频库作品页和在线详情现在按与文件列表相同的来源及清单规则校验路径。当前目录失效时，回到最近仍可见的祖先，并在目标列表就绪后恢复滚动位置。目录和来源切换后，旧请求的结果不会覆盖当前页面。实现见 [LibraryRepository.kt](../../app/src/main/java/com/nanahoshi/audioplayer/data/LibraryRepository.kt) 和 [WorkFolderLocation.kt](../../app/src/main/java/com/nanahoshi/audioplayer/ui/library/WorkFolderLocation.kt)。

### P3 · B 站收藏夹把分 P 下载任务数显示为视频数

选择一个三 P 视频可以新增三个下载任务，原提示却显示开始下载三个视频。收藏夹现在显示「已加入 3 个下载任务」，处理失败按视频计数，已有本地文件或任务时显示「已在本地或正在下载」。实现见 [FavoriteScreen.kt](../../app/src/main/java/com/nanahoshi/audioplayer/ui/library/FavoriteScreen.kt)。

### P3 · 文案审查记录与实际入口不一致

文案审查报告仍把「下载管理 → 字幕」写成缺失入口，B 站接口文档也引用了旧合集按钮名。已标明报告中的旧界面描述为修改前状态，记录字幕分段可用，并同步合集按钮名、混选删除和目录回退说明。见 [文案审查报告](../ui-copy-review.md)、[B 站接口文档](../bilibili-api.md) 和 [Android README](../../README.md)。
