# Japanese ASMR 整作下载、文章刷新与收录查询

单曲「下载」继续使用网页播放器的音频。作品「下载到本地」改用站点的专用 Download 入口。新版列表里的整段音频和各分轨文件全部保留。作品搜索只查询 DLsite 和 asmr.one，打开在线详情后再确认 JA 收录。

本文在 2026-11-19 审查后补齐了整作入口的验证契约、文件清单模型、发布/重下语义、刷新清理边界和验证返回路由。审查结论与默认取舍见第 5、6 节。

## 1. 整作下载和文件目录

### 1.1 入口、验证与任务挂起

- **按入口选择下载线路。** 单曲、多选曲目和听写前置下载沿用现有直链或 HLS 流程。作品页、作品菜单和普通父文件夹中对完整 JA 作品发起的下载，统一进入整作流程。保留多篇文章的「单篇／全部」选择，按归一化后的站内下载入口地址去重：多篇指向同一入口时只下载一份。
- **读取实际 Download 链接。** 优先从文章 HTML 解析 Download 链接（站内 `/dlc.php?...` 或跳转地址）；解析不到时使用文档已验证的 `https://japaneseasmr.com/dlc.php?f={RJ}`。入口地址只保存在内存，不落库、不写日志。若所选文章解析出多个不同入口，不自动选第一篇：弹出入口选择，由用户明确选择一份后只下载该入口；多篇解析到同一入口时仍只下载一份。
- **首次准备与已入队任务分开处理。** 首次整作下载在创建任务前完成：入口选择 → 原生读取（需要时进入下载验证页）→ 读取文件清单 → 显示文件数和总大小确认；用户确认后才建任务。已入队任务在重试、地址过期等再次遇到验证时，才置为 `FAILED + phase = "VERIFY"`，错误文案「需要验证后继续」，下载页提供「验证并继续」。任务或准备已取消时，迟到的验证结果直接丢弃，不再重新读取入口。
- **下载验证模式。** 现有验证页只认文章数字路径，需新增“读取下载文件”模式：
  - 允许加载 `/dlc.php`；
  - 用户完成验证后，用 JS 捕获 `location.href` 和页面 HTML/链接（大小上限沿用 512 KB）；
  - 页面若跳往站外主机，只捕获跳转地址，不在 WebView 里加载外站；
  - 原生解析捕获结果，按主机白名单识别 Buzzheavier / MEGA 链接；
  - 成功后将本次入口结果一次性放入内存（首次准备绑定准备标识，已入队任务绑定任务 id，短 TTL）；首次准备据此显示清单确认，已入队任务据此恢复；进程重启、TTL 过期或结果与当前作品/入口不符时，只有任务或准备仍有效才重新读取入口；已取消/已删除的操作只丢弃结果，不再恢复。
- **不传 Cookie。** 继续沿用“验证会话只属于可见网页”的约束；托管文件页和 MEGA API 按文档不需要 JA 会话。若某个主机实际要求网页会话，明确提示「该下载地址需要网页会话，暂不支持」，不要把 JA Cookie 导给原生客户端。2026-11-20 真机修订：Buzzheavier 托管主机例外，验证后仅在内存中复用 WebView 的 Buzzheavier Cookie 和 User-Agent 给同一托管主机的原生请求；不写日志、数据库或任务记录，JA 站点 Cookie 仍不进入原生请求。
- **主机白名单。** 只接受解析结果中落在 Buzzheavier 已知主机、MEGA 分享/API 主机上的地址；拒绝任意跳转地址。所有页面和文件请求不得携带 JA 登录凭证。

### 1.2 任务模型与调度

- 新增 `kind = "JAPANESE_ASMR_WORK"`，`trackId = 0`，`source = JAPANESE_ASMR`，`workKey = 规范化 RJ`，`workFolderId = 作品根`，`fileKey = 所选文章的 postId`；完成后 `localPath` 指向作品「下载文件」目录（与 DLsite 整包一致）。
- `fileKey` 持久化用户选中的文章编号，进程重启后仍能从该篇重新读取入口；MEGA 密钥、入口和临时地址继续只驻内存。重试和发布时核对 `postId` 仍属于该 RJ 的作品根，文章已被移除时明确失败。
- 同一作品只允许一个占用中的整作任务：`QUEUED`、`RUNNING` 或 `FAILED + phase = "VERIFY"`；普通 `FAILED`（包括用户中止）不占用名额。用户取消 A 入口后可直接选 B 入口新建任务，A 留在任务页由用户显式重试/删除；等待验证的任务需要先完成验证或删除，才能改选另一入口。查重与插入在同一事务内完成。单曲 JA 任务仍按 `postId + mediaKey` 查重，两者可并行；文件名和目录不冲突。
- 入队、显式重试和验证后继续共用同一个事务内的占用检查 `reserveWorkTask(workKey, excludeId)`：查询 `QUEUED`/`RUNNING`/`FAILED + phase = "VERIFY"` 时排除当前任务自身，避免等待验证任务查到自身而无法恢复；旧任务重试发现另一占用任务时不得抢占，提示已有任务或返回其 id。启动恢复扫描同样排除自身。
- `libraryTarget` 增加该 kind 分支：按 `workFolderId`/`workKey` 核对作品根仍在库，并核对 `fileKey` 的文章仍属于该根；入队、执行、重试、发布沿用 `requireRunningTarget`。
- `DownloadWork.slot()`：JA 整作任务用 `work = RJ`、`archive = false`、`exclusiveWork = true`。`archive` 仍只控制 DLsite 整包的全局互斥；`exclusiveWork` 让同一作品的整作任务在 `TaskPump.downloadStartDecision` 中串行（包括排队中的任务），但不占用全局 archive 位。仅设置 `work` 不会让两个普通任务串行，必须显式检查 `exclusiveWork`。任务内部逐文件串行，占用一个普通并发位。
- 进度沿用现有 `ProgressPhase`：读取入口（RESOLVING）→ 下载文件（DOWNLOADING，显示文件 n/m 和字节）→ 解压（EXTRACTING）→ 发布（IMPORTING）→ 清理（CLEANING）。`progressSummary` 只写计数、阶段、复用/跳过数量，不写 URL、MEGA 密钥或临时地址。
- 中止、失败和进程终止保留已完成暂存与已发布旧副本；启动时把 RUNNING 登记为中断，回收没有任务行引用的孤儿暂存。`deleteFailed` 回收本任务暂存和未发布的代次。
- 作品在任务执行中被移除：在发布前按 `libraryTarget` 核对失败，保留已发布旧副本，暂存按任务状态保留或回收。作品重新入库后，失败任务重试按 `(rj, path)` 重新绑定。
- `DownloadScreen`：整作任务像 archive 一样不可直接播放；补阶段文案、删除确认文案和「验证并继续」动作；通知同步显示进度或等待验证。

### 1.3 文件清单、目录与发布

建议仿照 `dlsite_original_works/entries` 新增两张表（最终以 Room 实体为准；21→22 迁移不设外键，可空列不设默认值）：

```sql
CREATE TABLE japaneseasmr_download_works (
  rj TEXT NOT NULL PRIMARY KEY,
  rootFolderId INTEGER,
  postId TEXT,          -- 展示归属文章
  directory TEXT,       -- 「下载文件」目录
  updatedAt INTEGER
);
CREATE TABLE japaneseasmr_download_entries (
  rj TEXT NOT NULL,
  postId TEXT NOT NULL,
  relativePath TEXT NOT NULL,
  kind TEXT NOT NULL,   -- FOLDER / AUDIO / FILE
  size INTEGER NOT NULL,
  sha256 TEXT,          -- 可用校验值；没有则 NULL
  localPath TEXT,
  packageKey TEXT,      -- 来源压缩包；直接文件为 NULL
  trackId INTEGER, fileId INTEGER, folderId INTEGER,
  PRIMARY KEY(rj, relativePath)
);
CREATE TABLE japaneseasmr_download_packages (
  rj TEXT NOT NULL,
  packageKey TEXT NOT NULL,   -- 包在入口列表中的稳定标识
  relativePath TEXT NOT NULL,
  size INTEGER NOT NULL,
  sha256 TEXT,
  localPath TEXT,             -- 包文件；解压后默认清理时为 NULL
  extractedAt INTEGER,
  publishedAt INTEGER,        -- 所有关联条目接受当前版本后才写入
  PRIMARY KEY(rj, packageKey)
);
CREATE INDEX index_japaneseasmr_download_entries_trackId ON japaneseasmr_download_entries(trackId);
CREATE INDEX index_japaneseasmr_download_entries_fileId ON japaneseasmr_download_entries(fileId);
CREATE INDEX index_japaneseasmr_download_entries_folderId ON japaneseasmr_download_entries(folderId);
CREATE INDEX index_japaneseasmr_download_entries_packageKey ON japaneseasmr_download_entries(rj, packageKey);
```

- **身份用 `(rj, relativePath)`**，`postId` 只记录归属文章。入口按 RJ 提供，多篇文章共入口时用 `rj + path` 才能稳定做到“重复下载复用原曲目编号”；按文章做键会在归属变化时改变身份。
- **目录归属（已确认）**：作品根下统一建一个「下载文件」目录（名称冲突时加后缀），所有文章共用；多篇文章共用入口时只建一份。音频、非音频和子目录都按站点相对路径镜像在它下面。
- **文件映射**：音频（扩展名 + `MediaMetadataRetriever` 可读）建 `tracks`；非音频建 `library_files`；目录建 `folders`。音频曲目 `source = JAPANESE_ASMR`、`asmrWorkId = 作品根`、`fileHash = null`、`localUri = 最终路径`，**不写 `japaneseasmr_media`**，避免被在线解析逻辑当成播放器音轨。曲目标题取原文件名，时长用媒体元数据回写，封面用文章封面。
- **路径安全**：统一 `/` 分隔、去掉前导斜杠；拒绝 `..`、绝对路径、空路径、控制字符和系统保留名；重名或大小写/Unicode 归一化冲突保留第一条并汇总提示，不整体失败。
- **发布**：先写入暂存目录，全部文件校验通过后在一个事务里建/复用目录、曲目、文件并 upsert 清单。未变化的条目复用原 `localPath`，不重复落盘；新增/变化条目使用新代次文件。提交成功后回收不再被任何清单行或曲目引用的旧文件；提交失败只清理新代次，旧目录不动。
- **重下**：每次请求都先解析当前入口并读取最新文件列表，再与清单逐项比较：`localPath` 非空、磁盘文件存在、长度和可用校验值一致才算“磁盘完好”；与当前远端列表的大小/校验值一致才算“远端未变”。只有当前列表的新增、变化和缺失文件都为零时才直接复用、不新建任务；否则建一个任务只补新增/变化/缺失文件，未变化条目保留原 `localPath`。已有文件能打开不能单独作为复用依据，否则会漏掉站点新加的分轨。远端没有校验值时只能按长度判断，并在结果中说明无法确认内容变化，提供手动重新下载入口。
- **改选入口与路径冲突**：用户改选另一入口时，如果新清单的同一相对路径已有文件且大小/校验值不同，先确认「该路径已有不同文件，是否替换？」。确认后按变化条目替换并保留曲目编号；取消则保留旧文件、跳过该路径并报告，不整体失败。拒绝的路径在清单保留旧版本，不把本次入口计为完整发布；下次重新评估并再次提示。替换旧文件前核对播放、队列和字幕任务引用，仍被使用的旧文件延迟回收。
- **压缩包版本**：清单另存 `japaneseasmr_download_packages`（`rj + packageKey`，记录包相对路径、大小、可用校验值、包文件路径、解压完成时间和完整发布时间），条目用可空 `packageKey` 关联。`publishedAt` 只表示包行当前 `size`/`sha256` 这一版本已完整发布，不能跨版本沿用。远端比较以包本身为准：包未变、`publishedAt` 非空且对应当前包版本、该包的解压文件齐全时直接复用，不重下包；包内文件缺失且包已被清理时重下该包、解压并只补缺失条目；包变化时重下、解压、逐项比较，替换变化文件并保留旧条目。远端无校验值时自动复用可按长度判断，但用户手动「重新下载」必须跳过长度复用，强制重下。用户拒绝替换某个路径时，该条目保留原文件、原 `size`/`sha256` 和原 `packageKey` 版本关联；如果包行已更新为新版本，必须清空 `publishedAt`；只有包行仍记录旧版本时才可保留旧日期。下次整作下载重新评估：已接受条目按新版本匹配，拒绝条目再次提示替换，不因包行已更新而跳过。
- **单文件删除**：`deleteLocalCopies` 对这类曲目只清 `localUri` 和清单行的 `localPath`（保留 `size`/`sha256` 作为远端期望值），保留清单行、曲目、目录和整作任务记录；播放时提示「该文件仅随整作下载提供，请重新下载整作文件」，不要落到空 URI。下次整作下载会把 `localPath` 为空的条目标记为缺失并补下。
- **作品移除/重导入**：清单行和下载记录像 `japaneseasmr_posts` 一样保留；重新导入时按 `(rj, path)` 回链仍存在的文件，重建目录和曲目身份。`deleteItems` 只删目录/曲目，需补回链逻辑。
- **接入点**：`StoredCatalog` 根目录与 `inside()`、`downloadWorkDirectory()`、启动清理与孤儿回收、`observeWorkTreeChanges` 的 invalidation 表清单都要加入新根/新表，否则发布后 UI 不刷新、文件也不会被管理。

### 1.4 Buzzheavier、MEGA 与压缩包

- **Buzzheavier**：下载列表 → 托管文件页 → 解析 `/<文件编号>/download?t=...` 和页面公布的校验值/长度 → 原生传输。`t` 只留内存。续传必须确认是同一文件：长度 + 校验值/ETag/Last-Modified 一致才发 `Range`；服务器回 200、`Content-Range` 起点不符或长度变化就重下该文件。没有校验值也没有 ETag 时不做跨重试续传，避免拼接两个版本。2026-11-20 真机修订：按钮响应可能是 `204 No Content` + `HX-Redirect`；必须在内建网页里用普通请求（不带 `HX-Request`/`HX-Current-URL`）跟随到 `audio/mp4` 等文件响应，否则会反复收到 204 + 跳转。浏览器确认的文件地址即使仍是 `/download?t=...` 也作为最终地址；原生首次用普通 GET（探测不带 `Range`），成功后再用 `Range` 续传，并缓存最终地址避免重复消耗令牌。仅对 Buzzheavier 主机在内存中复用 WebView 的 Cookie 和 User-Agent，JA Cookie 不进入原生请求。
- **MEGA（已确认：纯 Kotlin）**：实现公开单文件分享协议：解析 `mega.nz/file/...` 或 `/#!...!...`，读取分享信息，AES-CBC 解属性，AES-CTR 下载，完成后校验 MAC/长度；续传按探针已验证的 MEGA 传输路径从指定字节偏移读取并解密，CTR 计数器随偏移调整，不要把它写成 HTTP `Range` 请求（HTTP Range 只用于 Buzzheavier）。分享密钥只驻内存，进程重启后重新从入口页读取。MEGA 文件夹链接提示暂不支持。
- **压缩包**：ZIP/RAR 复用 `DlsiteArchiveExtractor` 的能力（抽出可复用封装，避免直接依赖 DLsite 专用入口）。支持单个 ZIP 或 RAR 分卷；加密包、7z、分卷异常、路径穿越、嵌套压缩包和解压炸弹分别提示或保留原文件。解压后默认不保留原压缩包（与 DLsite 一致），只保留解压文件。
- **单文件与多文件**：入口只有一个音频时直接建曲目；多个音频全部建曲目；ZIP/RAR 解压后按实际音频文件建曲目。整段音频和分轨文件都保留，即使内容重复。

### 1.5 下载管理、播放与字幕

- 整作下载的音频曲目接入现有播放队列、播放列表、下载管理和生成字幕；非音频文件只在作品文件区可见，不进入下载管理「音频」。
- `MediaItemFactory` 对 JA 曲目先取本地副本；「下载文件」曲目没有 `japaneseasmr_media` 行，本地文件有效时直接按文件播放。本地文件被删后不要回退到在线解析，明确提示重新整作下载。
- 听写/翻译身份使用 `japaneseasmr://file?rj={rj}&path={relativePath}`（或等价的曲目级稳定标识）；生成字幕按音频内容指纹复用，与播放器音轨重复时不会重复生成。
- 刷新清理只处理 `japaneseasmr_media` 曲目，绝不删除「下载文件」曲目。

## 2. 刷新文章、验证返回和失效清理

### 2.1 刷新入口与语义

- 在库内 JA 作品页新增「刷新文章」：当前位于某篇文章内时刷新该篇；位于作品根目录且有多篇时提供单篇或全部选择。文章文件夹到 `postId` 的映射用 `japaneseasmr_posts.articleFolderId`，不按文件夹名猜。在线详情的同名按钮使用同一刷新逻辑。
- 刷新期间保留已有目录和播放状态，按文章分别反馈新增、清理和保留数量。建议文案：「新增 X 条，清理 Y 条，保留 Z 条（有本地副本或正在使用）」。
- 新增仓储函数 `refreshJapaneseAsmrPost(postId, rootId, cleanup: Boolean): RefreshResult`。普通下载前同步、普通验证同步走 `cleanup = false`；显式刷新走 `cleanup = true`。现有 `importJapaneseAsmrPost` 保持非破坏性。
- 多篇「全部」刷新串行执行；中途遇到验证时停在当前篇，提示「《文章名》需要验证」，验证后继续剩余篇，不并发抓取。

### 2.2 自动清理

- **触发条件（已确认）**：完整读取了作品号相符的文章，并且解析结果完整（`JaArticle.complete`：`.cleanPlayer` 的每个播放器都有可用候选、没有因键冲突被 `distinctBy` 丢弃、没有旧式播放列表混入、至少有一个音轨）；新列表的音轨键集合与旧集合不同（新增、删除或替换都算）时，检查该篇旧的播放器曲目。空页面、结构异常、网络失败、验证失败、RJ 不符、解析不完整一律保留旧曲目，不清理。
- **先匹配后清理**：匹配分两遍。第一遍按 `mediaKey` 完全一致配对，旧键仍在新页面时优先保留原身份（即使旧路径被另一首新曲目使用）；第二遍只对剩余新旧条目做一对一的 `pathHash` 匹配。每项结果记为“已匹配（键/路径）”“资料不足（旧 `t:` 行没有 `pathHash` 且键不在新页面）”“歧义（多首同路径/多重匹配）”或“确认消失”。页面解析不完整时整篇不清理；页面完整时只有“确认消失”进入清理，资料不足和歧义只保留受影响曲目，其余确认消失的曲目可清理。旧 `t:` 行首次精确命中时补写 `pathHash`；补写前不因页面只给 `p:` 键而删除。播放、下载和验证返回使用同一张整篇匹配表，不单独判断路径唯一。
- **清理对象**：只限该文章的 `japaneseasmr_media` 曲目；同键/同路径确认同一曲目的沿用原曲目编号并更新资料。只有匹配结果为「确认消失」的旧键进入清理候选；资料不足或歧义保留。
- **同键刷新的队列/播放列表行为**：播放列表和已入库队列项保存的是 `trackId`，同键刷新不改变曲目编号，条目和顺序保持不变；在线播放时按旧 `(postId, mediaKey)` 经共享解析器（必要时用 `pathHash`）从刷新后的文章候选解析，因此旧条目会使用新地址，不做行替换。未入库队列项保存的是 `postId + mediaKey + mediaKind`（新行另有 `mediaPathHash`），同键但媒体类型在 DIRECT/HLS 间变化时可能仍是旧类型；刷新或播放时应同步更新匹配的队列行或重新解析。
- **同键但文件内容变化**：App 不比较音频内容，只按 `mediaKey` 判定同一音轨。已有本地副本时继续播放旧文件并跳过重新下载；要取得站点的新文件，需先删除本地副本再下载。字幕仍按原曲目和内容指纹保留。
- **无法确认同一曲目的新键**：即使新旧内容相同也视为两条曲目。旧曲目按清理规则处理（仅本地副本和当前项受保护），播放列表/队列中的非当前旧条目随曲目移除；新曲目不会自动替换旧条目，需要用户重新加入。
- **保护集合（已确认）**：只保护有效本地副本和播放器当前条目（暂停或缓冲中的当前条目同样保护）。队列和播放列表中的非当前旧曲目不保护：移除曲目时按现有级联/压缩规则清理对应队列和播放列表条目，并在结果中报告数量。进行中的下载/听写/翻译任务先停止或标注失败后再移除。
- **保留内容**：字幕文件、听写/翻译/下载任务记录不删；删除曲目和 `japaneseasmr_media` 行。清理前再次核对本地副本和当前播放状态。
- 计数定义：新增 = 新键；清理 = 实际移除；保留 = 页面已移除但因本地副本或当前播放而保留的旧键。仍在页面上的同键曲目只算更新，不计入保留。

### 2.3 播放时「清除失效音频」

- 需要带类型的失效异常，只在以下情况触发：文章页明确 404/410；页面解析完整（`JaArticle.complete`）、RJ 匹配且按 §2.5 的匹配结果为「确认消失」；所有主媒体候选都明确 404/410（HLS 指清单候选）。验证/403、超时、限流、5xx、单个 HLS 分片失败、解析不完整、资料不足或匹配歧义都不算失效，继续走原错误提示，不弹清理框。
- 由 `PlaybackService`/`PlayerClient` 暴露带类型的失效事件，播放页错误区弹「清除失效音频？」；不要靠匹配错误字符串。
- 确认前再核对：本地副本是否出现、曲目是否还在、是否仍是当前队列项。已入库曲目移除曲目及对应播放列表/队列条目；未入库曲目只移除队列条目。若删的是当前项，停止播放并清理 `playback_state`。取消则保留曲目和原错误。
- 字幕文件、听写/翻译记录保留；对应未完成下载任务停止或标注，不留永远等不到文件的排队任务。

### 2.4 验证返回

把 `Routes.JapaneseAsmrVerification` 从「url/rj/queueId/mediaKey」扩展为携带操作身份：

- `operation`：`PLAYBACK` / `REFRESH` / `SYNC` / `DOWNLOAD`；
- `postId`、`expectedRj`、`queueId`、`mediaKey`、`taskId`、`prepId`（首次整作下载的准备标识）；
- 返回时按操作分流：
  - `PLAYBACK`：原队列项仍是当前项、曲目仍存在，且整篇匹配结果把该队列项映射到本文一条媒体（`MatchedByKey` 或 `MatchedByPath`），才恢复播放；`Gone`/`InsufficientIdentity`/`Ambiguous` 不恢复，按原错误提示处理。
  - `REFRESH`：执行带清理的刷新，回到原页面并提示计数；
  - `SYNC`：只同步曲目，不清理；
  - `DOWNLOAD`：有 `taskId` 时恢复已入队任务；只有 `prepId` 时完成首次准备并显示文件清单确认，不直接建任务。任务或准备标识已被删除/替换时丢弃迟到结果。
- 未入库作品继续留在在线详情，不自动保存。不要再无条件跳转 `Routes.onlineWork(...)`；当前 `MainActivity.kt:648-662` 会把库内刷新/普通同步都带回在线详情。

### 2.5 标题、描述与文件命名的一致性（2026-11-19 补充）

- **来源**：曲目标题取 `.cleanPlayer` 播放器元素的 `title` 属性，描述取 `descr`；标题为空且整篇只有一个播放器时回退到 `h1.page-title`。`mediaKey` 优先用标题+描述的哈希（`t:`），标题或描述缺失/重复时退化为首个候选 URL 路径哈希（`p:`）。下载文件名由 `tracks.title` 生成，不是远端文件名（`DownloadCenter.kt:905-907`）。
- **问题**：验证页读取的是 WebView 动态 DOM，刷新走原生静态 HTML；同一文章可能在一侧有播放器 `title`/`descr`，另一侧为空并回退到 RJ 号。标题/描述变化会改变 `mediaKey`，被当成新曲目；即使键不变，文件名也会随标题变化。App 不比较音频内容，也不会覆盖旧文件，所以同内容可能留下两个文件。只在入库时复用旧键也不够：播放和单曲下载目前按旧键在新文章里精确查找，键不一致就会失败。
- **统一身份解析**：
  - `JaMediaRef` 增加 `pathHash`（首个候选 URL 的 `encodedPath` 哈希，忽略域名/查询/fragment，取与 `p:` 键相同的 16 位）以及 `hasTitle`/`hasDescription` 标志；`JaArticle` 增加 `complete` 标志（定义见 §2.2）。
  - 21→22 给 `japaneseasmr_media` 增加可空 `pathHash`，并建 `(postId, pathHash)` 索引。新行写入；旧 `p:` 行的键后缀可当作 `pathHash`；旧 `t:` 行没有路径信息，键不在新页面时记为“资料不足”并保留，精确命中时补写 `pathHash`，不自动合并已有重复曲目。
  - 新增共享解析器 `resolveStoredJaMatches(article, postId, dao)`：一次加载该篇全部已入库媒体，按两遍规则生成整篇 `Map<旧 mediaKey, JaMatchResult>`（`MatchedByKey` / `MatchedByPath` / `InsufficientIdentity` / `Ambiguous` / `Gone`），而不是逐条“在页面里找路径唯一”。播放、单曲下载、刷新和验证返回都读取这同一张匹配表：旧 A 的键消失、新 B 占用了 A 的旧路径但 B 已按精确键匹配到旧 B 时，A 不会误用 B；只有 A 自己在第二遍获得唯一路径匹配才算同一曲目。已入库曲目使用这张表；未入库队列项没有库行，按自身的 `mediaKey` 和 `mediaPathHash` 查找，路径匹配同样要求本文内唯一。
  - `mediaPathHash` 只作为播放查找线索，不进入字幕/翻译身份。未入库队列项在 21→22 增加可空 `mediaPathHash`，入队时写入 `JaMediaRef.pathHash`；`RemotePlayable`、播放 URI（如 `japaneseasmr://audio?post=...&media=...&path=...`）、`QueueDao.snapshot()`/`observe()` 携带它。`jaAudioIdentity()`/`jaIdentity()` 继续使用 `japaneseasmr://audio?post=...&media=...` 原格式，老字幕、翻译和覆盖记录不受影响。
  - 未入库项按路径回退时，先排除整篇匹配表已经分配给其他已入库身份的媒体，以及队列中其他未入库 JA 项按精确键/路径占用的媒体；排除后仍不是唯一候选或没有候选时，提示重新打开文章/重新入队，不按路径播放。未入库项没有库行，但仍使用同一张匹配表并结合队列身份判断占用。
  - 入库/刷新采用两遍匹配：第一遍按 `mediaKey` 完全一致配对，旧键仍在新页面时优先保留原身份，即使旧路径被另一首新曲目使用；第二遍只对剩余新旧条目做一对一的 `pathHash` 匹配。命中旧条目时沿用旧 `mediaKey`，保留曲目编号、`localUri` 和字幕关系；新媒体只在无匹配时生成新键。匹配不唯一或旧 `t:` 行没有 `pathHash` 时不做路径认领。
  - 标题/描述：同一路径确认同一曲目时，保留键、曲目编号和现有本地文件名；新媒体标题有效且不同（播放器 `title` 非空且不是纯 RJ）时只更新显示标题，否则保留旧标题；描述只参与首次建键，命中后不重算。只有身份无法确认（无路径/歧义）时才生成新键和新曲目。标题回退不得把仅由 RJ 号组成的文章标题当作曲目标题。
  - 反向场景（先原生入库得到 `p:`/RJ 标题，后验证页读到完整标题和描述）同样由 `pathHash` 命中旧键；保留旧键，允许用完整标题更新显示标题。仅缺描述、仅缺标题、两处都缺都走同一路径。
  - 没有 `pathHash`、路径被站点更换、同篇多个媒体路径相同或匹配不唯一时，不猜：保留旧曲目并新增。单媒体对单媒体本身不构成复用证据，必须有路径哈希或键完全一致。
- **清理与匹配的关系**：先完成上述身份匹配，再按 §2.2 清理。页面解析不完整时整篇不清理；页面完整时只清理匹配结果为 `Gone` 的曲目，`InsufficientIdentity`/`Ambiguous` 只保护受影响曲目，其余确认消失的曲目可按规则清理。播放失败也不因键缺失直接弹清理框（见 §2.3）。
- **文件名**：继续使用曲目标题；同一路径确认同一曲目时保留旧 `localUri` 和旧文件名，只更新显示标题。键确实变化且无法确认同一曲目时才新建文件，旧文件按现有规则保留，可按下载管理规则删除本地副本；曲目本身不能单独从作品内移除。不因为内容相同而覆盖、删除或合并旧文件；内容比较不属于当前身份规则。
- **回归**：
  - 验证页缩减 HTML（`title` 非空）与原生完整 HTML（`title` 为空、`h1` 为 RJ）得到相同 `mediaKey`、标题、曲目编号和本地文件路径。
  - 反向顺序：先原生入库（`p:`/RJ），再验证页读到完整标题和描述，仍命中旧键并更新标题，不新增曲目。
  - 仅缺描述、媒体路径相同但标题不同、同篇多条路径相同、单媒体但路径不同：分别断言复用/不复用。
  - 旧键仍在新页面、但旧路径被另一首新曲目使用时，精确键优先保留旧身份；新曲目不能凭路径抢走旧键。
  - 播放、单曲下载在刷新后按旧键仍能找到新文章中的对应媒体（通过 `pathHash`）。

- **标题/描述一致性。** 同一文章的验证页缩减 HTML 与原生完整 HTML 应得到相同 `mediaKey`、标题、曲目编号和本地文件路径；回退标题（空/纯 RJ）不新增曲目；同一路径确认同一曲目时，有效标题只更新显示标题，保留键、编号和本地文件名；只有身份无法确认时才生成新键并保留旧曲目；同内容不自动覆盖旧文件；单媒体但路径不同不构成复用证据。
- **匹配顺序与旧行保护。** 旧键仍在新页面时优先于路径匹配；新曲目占用旧路径不能抢走旧身份。播放、下载和验证返回读取同一张整篇匹配表：旧 A 的键消失、新 B 占用 A 的旧路径但 B 已精确匹配旧 B 时，A 不误播 B。未入库队列项按路径回退时同样排除已分配给其他已入库身份或队列中其他未入库项的媒体；排除后不能唯一确认时提示重新打开文章/重新入队，不按路径播放。旧 `t:` 行没有 `pathHash` 且新页面只给 `p:` 键时，刷新不删除、播放不弹失效框；下一次精确命中补写 `pathHash`。解析不完整整篇不清理；解析完整但个别曲目资料不足/歧义时只保留受影响曲目，其余 `Gone` 可清理。
- **任务状态与首次流程。** `QUEUED`、`RUNNING` 和等待验证占用名额，普通失败/中止不占用；首次下载在入口选择、验证和清单确认后才建任务；已入队任务再次验证才挂起；任务或准备已取消/删除时只丢弃迟到结果，只有仍有效的操作遇到结果过期才重新读取入口。入队、重试、验证后继续共用事务内占用检查并排除自身：等待验证任务能恢复自己；旧 A 重试发现 B 占用时不抢占。
- **压缩包与入口替换。** 包版本未变且解压文件齐全时复用；缺文件且包已删时重下包；包变化时重下并逐项替换；无校验值时手动重下跳过长度复用。改选入口时同一路径内容不同先确认替换，取消保留旧文件。拒绝替换的条目保留旧版本关联；包行更新为新版本时必须清空 `publishedAt`，只有包行仍是旧版本时才可保留旧日期，不得把新版本误判为完整发布。下次重新评估并再次提示。
- **身份字符串兼容。** `mediaPathHash` 只用于播放查找；`jaAudioIdentity()`/`jaIdentity()` 保持 `japaneseasmr://audio?post=...&media=...` 原格式，老字幕和翻译记录仍能匹配。
- **资料不足的保留范围。** 旧 `t:` 曲目身份资料不足时保留在作品内，接受可能长期保留；现有音频库禁止单独移除作品内曲目，计划不新增删除入口，也不扩大单曲删除权限。只能删除其本地副本或整部作品，或等精确命中补写 `pathHash` 后再按确认消失清理。
- **搜索与兼容。** 验证搜索及分页没有 JA 请求，进入详情才开始核对收录；保存作品不触发隐式 JA 搜索；覆盖无匹配、验证失败、连接失败和迟到响应。通过 21→22 迁移测试，确认原曲目、下载文件、队列和字幕关系仍可使用。在 Android 16 模拟器运行定向测试，同步更新 README、JA 接口文档和项目指南（数据库版本 22）。
- **术语。** 下载列表里的音轨文件统一叫「分轨文件」；「章节」只指文章页的时间点，避免实现时混用。

## 5. 已确认决策（2026-11-19 审查）

1. 「下载文件」目录统一放在作品根目录下，所有文章共用；清单记录归属文章，不按文章分裂目录。
2. 刷新自动清理在完整读取、RJ 相符且音轨键集合有变化时执行（包括纯删除）；同键复用，缺失键按保护规则处理。
3. MEGA 公开单文件分享用纯 Kotlin 实现协议；不引入 MEGA 官方 C++ SDK，不新增 NDK 依赖。
4. 自动清理只保护有效本地副本和播放器当前条目；队列/播放列表中的非当前旧曲目移除并报告数量。

## 6. 其他默认取舍（未另行确认时按此实施）

- 清单主键用 `(rj, relativePath)`，`postId` 只记录归属文章。
- 详情 JA 查询首页有匹配即停；不为了跨页收集额外等待多个 10 秒。
- 压缩包解压后不保留原包；加密包、7z 明确提示暂不支持。
- 整作入口不可用、仅文件夹 MEGA 或解析失败时，错误提示中提供「改用播放器音轨下载」入口。
- 下载前显示文件数和总大小（能取得时）确认；用户取消不建任务。
- 非音频文件不进入下载管理「音频」，只在作品文件区可见。
- 多篇「全部」刷新中途遇到验证时停在当前篇并提示，验证后继续剩余篇。
- 已完成的整作任务行保留在下载页；不可播放，可查看进度/结果。
- 播放器音轨与整作下载文件内容重复时两套都显示，不自动去重；「下载文件」目录名用于区分。
- 等待验证用 `FAILED + phase = "VERIFY"` 表示，不新增 `DownloadStatus` 枚举。
- 整作任务调度键为 `work = RJ`、`archive = false`、`exclusiveWork = true`；任务内部逐文件串行。
- 新文件根为 `filesDir/japaneseasmr-downloads/{rj}/`，暂存与发布代次都在其下；必须加入 `StoredCatalog`、启动清理和下载目录白名单。
- 「下载文件」曲目的听写/翻译身份使用 `japaneseasmr://file?rj={rj}&path={relativePath}`；生成字幕仍按音频内容指纹复用。
- 整作任务发布成功后，站点新清单中已消失的旧文件保留并提示，不自动删除。
- 同一作品解析出多个不同下载入口时，由用户在入口选择中明确选一份；同一入口的多篇文章仍去重。
- 整作任务 `fileKey = 所选文章 postId`；同一 RJ 按 `QUEUED`、`RUNNING`、等待验证去重，普通失败/中止不占用名额；入队、重试、验证后继续共用事务内占用检查并排除自身；`exclusiveWork` 参与同作品串行。
- `japaneseasmr_media` 增加可空 `pathHash` 和 `(postId, pathHash)` 索引；旧 `p:` 键后缀可回填，旧 `t:` 键无 `pathHash` 且新页面只给 `p:` 时按“资料不足”保留，精确命中后补写 `pathHash`。
- 匹配顺序为先全量精确键、再对剩余条目做一对一路径匹配；精确键优先于路径，新曲目占用旧路径不能抢走旧身份。整篇生成带类型匹配结果（键/路径/资料不足/歧义/确认消失），播放、下载、刷新和验证返回共用同一张表。未入库队列项按路径回退时也排除已分配给其他已入库身份或队列中其他未入库项的媒体；无法唯一确认时提示重新打开文章/重新入队。
- 单媒体对单媒体本身不构成身份复用证据；必须有路径哈希或键完全一致。
- 已有重复曲目/文件不自动合并。作品内曲目不能单独从音频库移除，计划不为“资料不足”的旧曲目新增删除入口，也不扩大单曲删除权限；接受旧曲目可能长期保留。只能删除其本地副本或整部作品，或等身份资料足够后按确认消失清理。下载文件副本按下载管理规则处理。
- `saveOnlineWork` 不再隐式查询 JA；MEGA 续传用已验证的字节偏移路径，不是 HTTP Range。
- 同一路径确认同一曲目时保留旧键、旧 `localUri` 和旧文件名；有效标题只更新显示标题，不改键和文件名；只有回退标题（空或纯 RJ）不覆盖已有标题。标题回退不使用纯 RJ 号。
- 首次整作下载在入口选择、验证和清单确认后才建任务；已入队任务再次验证才挂起；占用状态不含普通失败/中止。任务或准备已取消/删除时只丢弃迟到验证结果，只有仍有效操作遇到结果过期才重新读取入口。
- 压缩包记录包版本；包未变且解压文件齐全复用，缺文件且包已删则重下包；无校验值时手动重下跳过长度复用。拒绝替换的条目保留旧版本关联；包行更新为新版本时必须清空 `publishedAt`，只有包行仍是旧版本时才可保留旧日期；下次重新评估并再次提示。
- 改选入口时同一路径内容不同先确认替换；`mediaPathHash` 只用于播放查找，`jaAudioIdentity()`/`jaIdentity()` 格式不变。
- Buzzheavier 的按钮请求可能是 `204 + HX-Redirect`；用普通请求（不带 HTMX 头）跟随到文件响应，不能按 `/download` 路径丢弃已确认的文件地址。浏览器确认后的最终地址交给原生，首次普通 GET、确认可读后才用 `Range`。
- 仅对 Buzzheavier 主机在内存中复用 WebView 的 Cookie 和 User-Agent；JA 站点 Cookie 不进入原生请求。验证失败重开当前 Buzzheavier 文件页，不退回 JA 入口；清单读取最多重试 3 轮。
- 进入 Buzzheavier 托管页后自动依次读取待处理文件，浏览器保持打开；不要求逐页点「读取下载文件」，只在真正出现验证时等待用户操作。
